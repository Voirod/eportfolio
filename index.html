GRADIENT DESCENT
MATHEMATICAL & ALGORITHMIC ASPECTS

A deep analysis of the Gradient Descent algorithm — mathematical theory and practical implementation in Python — applied to detecting plastic bottle pollution at sea. We built a custom MLP neural network from scratch and trained it on a 6,000-image ocean dataset, then benchmarked it against a TensorFlow reference model.

Key Skills
  • Algorithm Implementation — Classic, stochastic & momentum-based Gradient Descent in Python.
  • Neural Network — Custom MLP (Reseau & Neurone classes) trained on MNIST + custom dataset.
  • Comparative Analysis — Custom model (87%) vs TensorFlow (99.89% precision).
  • Ecological Impact — CarbonTracker to measure kWh and CO₂ cost of the AI.
  • Collaborative Dev — Git, Overleaf, Notion within a six-person team.
Reflection

We proved technical feasibility but found that more complex CNN models carry significantly higher energy costs — and that detecting bottles alone has limited environmental impact without collaboration with field specialists.

P2

School Project · Semester 5 · Group of 3 · ~31h/person · Imperative Programming · Ada

ROUTING TABLE
STORAGE & EXPLOITATION IN ADA

Design and implementation of a router's routing table in Ada, carried out during the fifth semester at ENSEEIHT as part of the Imperative Programming module. Over several weeks, we implemented, evaluated, and compared multiple approaches to exploiting a routing table through different refinements, modules, scenarios, and test suites.

The project was structured around three routers of increasing complexity: a Simple Router (direct table lookup), a Linked-List Router (LL) using a generic linked-list module (LC), and a Tree-based Router (LA) using a binary tree structure. Two distinct caching systems were also implemented and benchmarked — one linked-list-based (Cache_LC) and one tree-based (Cache_Arbre).

Key Skills
  • Ada Programming — Modular architecture with .ads/.adb separation, generic packages, and strong typing.
  • Data Structures — Generic linked lists, binary trees, and array-based tables for route storage.
  • Network Fundamentals — IP addressing, routing tables, next-hop resolution, and packet forwarding logic.
  • Caching Strategies — Design and comparison of two cache implementations (LC vs. Arbre).
  • Software Refinement — Iterative stepwise refinement methodology applied throughout the project.
  • Collaborative Work — Team of 3, task division, deadline management, and LaTeX/Overleaf reporting.
Reflection

Despite a modest initial interest in the topic, the technical depth of this project proved genuinely rewarding. I significantly improved my fluency in Ada and gained a concrete understanding of how routers handle packet forwarding. The key personal takeaway was the importance of setting clear deadlines within a team — structured organization was what made it possible to meet objectives within the allocated time.

P3

School Project · Semester 5 · Imperative Programming · C · SDL2

DIJKSTRA'S ALGORITHM
PATHFINDING ON A HEIGHTMAP

Implementation of Dijkstra's shortest path algorithm in C, applied to a weighted grid representing a terrain heightmap. The project goes beyond the classic algorithm: the cost function incorporates both Euclidean distance between grid nodes and positive elevation gain, so the computed path reflects real traversal effort across varying terrain.

The program takes a .grille file as input — encoding the terrain's width, depth, and altitude values — then visualises the grid and the computed optimal path in an interactive SDL2 window. Several terrain presets were included: a flat grid, a walled maze (murs.grille), and a mountain landscape (montagne1.grille).

Architecture & Key Modules
  • dijkstra.c/.h — Core algorithm: priority-queue loop, cost computation (distance + elevation gain), recursive path reconstruction via construire_chemin_vers.
  • grille.c/.h — Heightmap data structure (width × depth float array), neighbour retrieval with altitude-threshold filtering.
  • liste_noeud.c/.h — Linked-list of nodes storing coordinates, predecessor, and cumulative cost; used as both the to-visit queue and the visited set.
  • app.c + SDL2 — Graphical rendering pipeline: viewport, window management, animated path highlight, mouse/keyboard event loop.
  • grille_file.c — File I/O to load terrain grids from disk; includes a random terrain generator.
  • Makefile + test suite — Separate test binaries for each module (test_dijkstra, test_grille, test_liste_noeud, test_coord).
Reflection

This project was my first serious experience with C at this scale — managing dynamic memory manually, separating header specifications from implementations, and integrating a graphical library. Implementing Dijkstra from scratch, rather than using a library, forced a deep understanding of the priority queue logic and the path reconstruction step. The visual output via SDL2 was particularly rewarding: seeing the algorithm explore the terrain and highlight the optimal path made the abstract algorithm concrete.

P4

School Project · Semester 6 · Individual · Networks · YANE / Linux / Quagga

SIMPLIFIED ISP
NETWORK ARCHITECTURE

Design and deployment of a complete, virtualised ISP (Internet Service Provider) infrastructure using YANE — a Linux-based network emulation environment running Docker containers and network namespaces. The architecture mirrors a real-world FAI: a redundant core network, two client LANs behind configurable boxes, DMZ zones hosting a web server and a DNS server, and full inter-network routing.

All addressing used a personal IP block assigned at project launch (42.6.251.0/24), carefully subneted across every segment. The project was validated through a live oral demonstration with hands-on testing of every service.

Key Skills
  • IP Addressing & Subnetting — Full addressing plan across 8+ subnets (/28 blocks) with no overlap.
  • Static & Dynamic Routing — Static routes first, then RIP v2 (Quagga/ripd) on all three FAI routers for dynamic convergence.
  • DHCP Configuration — ISC DHCP server on each BOX to assign addresses to client LANs (e.g. 192.168.89.0/25).
  • DNS — BIND9 — Authoritative zone file for monsupersite.com, A records resolving to FAI web server (42.6.251.98).
  • Web Services — Apache HTTP server in a DMZ, plus a second user-hosted web server accessible cross-client.
  • Firewall — iptables — FORWARD chain on the Services Router: default DROP policy, selective ACCEPT for TCP port 80 to the web DMZ + stateful ESTABLISHED/RELATED return traffic.
Reflection

This was my first end-to-end infrastructure project — building every layer from addressing to application services. The most challenging part was getting RIP to converge correctly while iptables rules didn't block legitimate return traffic. Working in a virtualised environment closely resembling real equipment (Docker + Linux namespaces) gave me a solid, practical foundation in network administration that complements the theoretical coursework.

School Project · Semester 6 · Group of 8 · Object Technology · Java Swing · Agile

NUTRICOACH
METABOLIC REGULATION ASSISTANT

NutriCoach is a full Java Swing desktop application for metabolic self-regulation through the balance of nutrition, sport, and wellbeing. Built over three Agile iterations by a team of 8, the project covers nutritional goal calculation (Harris-Benedict formula), weekly sport planning, statistical tracking with a logarithmic evolution model, and a multi-role user account system — all persisted to CSV and flat-file storage with no external database dependency.

My personal contribution centred on the assistantNutritionnel module — a polymorphic food class hierarchy (Aliment → AlimentPesable / AlimentLiquide / AlimentProportion), a recipe filtering engine, and dynamic portion adjustment to meet the daily caloric target. In iteration 3 I also led the architectural refactoring of FctAppModules and GestionFichier to separate static profile data from dynamic tracking history, resolving team-wide Git conflicts.

Key Skills
  • Object-Oriented Design — Polymorphism, abstract classes, design patterns: Façade (FctAppModules), Strategy + Observer (BlindMode), CardLayout navigation.
  • Java Swing UI — Multi-page application with JFrame, CardLayout, dynamic theming (light/dark), custom date fields, real-time filtering and responsive image display.
  • Mathematical Modelling — Logarithmic weight-evolution curve f(x) = ln(x) replacing linear model; streak algorithm for consecutive workout tracking.
  • Agile / SVN — 3 iterations with individual iteration reports, team point scoring, full repository restructuring between sprints.
  • Data Persistence — CSV-based recipe and sport databases, per-user flat-file accounts, dynamic graphique.png generation at runtime.
  • Accessibility — BlindMode via Strategy pattern: switchable numeric vs. screen-reader-friendly display without modifying existing UI classes.
Reflection

This was my first large-scale object-oriented project in a team of 8 — the scale introduced real coordination challenges. The architectural refactoring in iteration 3 was the most technically demanding part: decoupling modules written independently required enforcing strict interface contracts across the team. Working through those constraints gave me a strong foundation in software design principles and collaborative development under an Agile workflow.

P6

School Project · Semester 6 · Individual · OS & Systems · C · Unix

MINISHELL
UNIX COMMAND INTERPRETER IN C

Development of a simplified Unix shell interpreter in C, covering all the fundamental mechanisms of an operating system: process creation and management, signal handling, file I/O redirections, and inter-process communication via pipes. The project was built progressively across six TP sessions, each adding a new layer of system-level functionality on top of the main read-eval loop.

The interpreter uses the readcmd library to parse the input line into a cmdline structure — handling special tokens (&, |, >, <) — then executes each fragment via fork / execvp, with the parent optionally waiting or backgrounding the child.

Implementation Steps
  • TP1 — Processes — Main read-eval loop, fork + execvp for command execution, waitpid for synchronisation, built-in exit.
  • TP2 & TP3 — Signals — Signal handling with sigaction: SIGINT/SIGCHLD, background process management (&), zombie reaping.
  • TP4 — Redirections — I/O redirections (> / <) via open + dup2, file descriptor management in child processes.
  • TP5 & TP6 — Pipes & Select — Command chaining with pipe + dup2 for piped fragments, multiplexed I/O with select.
  • Readline integration — Command history via GNU readline, compiled with strict flags (-Wall -Wextra -Werror -pedantic).
  • Memory management — Systematic free of readline allocations and cmd_dispose to prevent leaks.
Reflection

Building a shell from scratch made previously abstract OS concepts immediately concrete — every fork and pipe had a visible effect in the terminal. The most demanding part was correctly orchestrating signal handling alongside background processes: avoiding race conditions between SIGCHLD and the main loop required a precise understanding of process state and kernel scheduling. This individual project was a strong exercise in low-level C and careful systems thinking.
